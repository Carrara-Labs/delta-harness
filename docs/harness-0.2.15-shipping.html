Delta Harness · 0.2.15 · what ships and how we prove it

Shipping 0.2.15

Nine changes, read three ways — plain, technical, and exact. Then the regression battery, because the point of this release is that unattended agents stop losing work, not that they start losing it differently.

Two of these fix damage we have already measured on paying lanes. Four make an invisible failure visible. Three are configuration and safety.

Nothing in the release needs a design pass, and the highest regression risk is not in the two big items — it is in the small one that moves files.

Read this first

The release in one paragraph

Right now a long-running agent has two silent ways to waste your money. If its context fills up mid-conversation it can quietly go back to answering an older question and never say so. And if it runs out of budget it throws away everything it already finished and returns a line of counters. We have measured both on Aperture's client lanes: 42 runs did the wrong work, and 11 runs binned $141 of finished work.

0.2.15 fixes both, then closes the gaps that let them hide for weeks — chiefly that nothing anywhere told an operator which tools were actually working. The rest is a provider fix that unblocks Ferni's migration, a safety default, and three small knobs.

The nine

What we are shipping

Each one three times: what it means, what is happening, and the exact change.

D-1

The agent stops answering the wrong question

measured damage
In plain terms

When a conversation gets long, the agent summarises the old parts to make room. While doing that it re-reads "the original request" — and it fetches the first thing ever said in that conversation instead of what you just asked. It then answers that instead, confidently, with no error. On Aperture this happened to 42 runs of paid client work.

What is actually happening

Compaction pins a trusted task block into the summary so the agent does not lose its goal. The query that builds it selects the session's first run. That is right for a one-shot task run, where run one is the task, and wrong for every session holding more than one request — which includes every Telegram thread and 23 of 71 sessions on our busiest lane.

The change
compaction.ts:167  SELECT request FROM runs WHERE session_id = ? ORDER BY seq LIMIT 1
→  SELECT request FROM runs WHERE id = ?  // opts.anchorRunId, already threaded

and delete the fallback: 42 of 42 pins under the old query were the wrong task,
so no pin is safer than a stale one. Single-request sessions stay byte-identical.
D-9

Running out of budget stops destroying the work

measured damage
In plain terms

When an agent hits its spending limit it currently replies with nothing but a line of numbers — even though everything it produced is sitting on disk. Eleven Aperture runs died this way: 771 tool calls, $141, and two hours forty minutes of finished client work, thrown away silently.

What is actually happening

The budget guard builds a diagnostic string and finalises the run with that string as the entire output. The spill files, the artifact ledger compaction maintains precisely so pointers survive, the plan, and any child summaries are all still on disk — nothing offers them. Then the same internal string is delivered to the human wrapped in "try again in a moment", which reproduces the failure exactly.

The change
run.ts:780-783, 936-939
finalize(…, "failed", selfWriteNote(why), …)  // the counters ARE the answer
→ finalize(…, "failed", { user, diagnostic }, …)

user   → the plan + the artifact ledger + what to do instead
diagnostic → the counters, into runs.error and the error event as today

ledger covers BOTH families: .delta/spill/ and research/ — the exhausted run
orphaned 26 files AND 13 research dirs. It must NOT list scratch/, which is
wiped at run termination and would be gone before anyone read the path.
D-3 + D-2

You can finally see which tools actually work

makes failure visible
In plain terms

You tell an agent which tools it may use. Some of those quietly never switch on — a missing key, a missing setting — and nothing tells anyone. Delos configured 16 tools and was running 13. One of the missing ones cost 724,804 tokens in a single message, because when a tool errors the model does not stop, it improvises around it.

What is actually happening

The allowlist is a ceiling, not a guarantee: scheduling tools need a control-plane URL, code needs a resolvable binary, web_search checks its credential only at call time. /v1/status reports version, model, budget, MCP servers, vault and self-file fullness — and no tool list at all.

The change
server.ts:443  /v1/status gains three lists, read LIVE like vault and self:
  registered  offered to the model this run
  unusable   registered but a call would fail now — may fix itself, no restart
  omitted    never registered; only a restart changes it

plus ONE stderr line at boot when anything is omitted or unusable.
NEVER de-registration: credentialFor reads env OR the vault per call, so a key
handed to a running agent works immediately. Removing the tool breaks that.
D-12

Delegation works on the Codex subscription

unblocks Ferni
In plain terms

An agent on a ChatGPT/Codex subscription cannot hand work to helper agents at all — every single one fails instantly, while the main agent works fine, so it looks like it is fanning out when it is doing nothing. One run started 24 helpers, got 24 failures, and paid for all of them.

What is actually happening

Child calls attach an output-size cap. That backend rejects the parameter outright at any value, returning a 400 which classifies as a bad request rather than a temporary one, so the Anthropic fallback in the chain is never tried. Parent turns never send the cap, which is why the same connection works for one and not the other.

The change
provider.ts:1600  if (req.maxTokens) body.max_output_tokens = req.maxTokens
→ if (req.maxTokens && acceptsMaxOutputTokens(cfg.baseUrl)) …

a fourth sibling beside hostMatches / acceptsPromptCacheKey /
usesMaxCompletionTokens at provider.ts:748-761. DENYLIST chatgpt.com, not an
allowlist of openai.com — OpenAI proper accepts the field. Children then run
uncapped; the parent budget already bounds them.
D-7

Agent scratch files stop landing in your documents

highest regression risk
In plain terms

The engine writes big temporary files — raw web pages, research output, the model's own notes — into the agent's working folder. When that folder is a synced document vault, untrusted web content gets committed to git and pushed to your phone, and machine output lands next to human notes. This adds a setting to put scratch somewhere else.

What is actually happening

Three artifact families are rooted at the workspace, each with its own cleanup site, and one of them is a directory the model is explicitly told to write into. Moving the root is the easy half. The hard half is that compaction derives spill paths from the run's identity to shrink old messages safely — change the root and every pre-existing message stops matching, so the context stops shrinking with no error at all.

The change
DELTA_SCRATCH_DIR, defaulting to the workspace → existing deploys unchanged.

family          write            wipe              wiped when
spill           tools.ts:158    queue.ts:437    ephemeral only
research        research.ts:275  queue.ts:443    ephemeral only
model scratchpad  the model      queue.ts:403    every run

Each family moves its write AND wipe site in the same commit, or not at all.
demoteSpilled tries the new root, then the legacy one, once. research/ becomes
.delta/research/ so no operator has to write an ignore rule that can misfire.
D-8

A delegated coding CLI stops inheriting your inbox

safety default
In plain terms

When the agent hands a coding task to the Codex CLI, that CLI is signed in to a personal ChatGPT account — and inherits every connector on it. Asked to prove its Gmail access was off, a delegated session listed 6,913 real messages with write scope. Nothing on the machine granted that.

What is actually happening

The connection lives server-side on the auth token, so no credential on disk and no MCP server is involved. An agent deliberately given no send-capable tool could send mail as its owner in one hop. This matters now because Quarry Brain agents will have code.

The change
config.ts:306  codeCli default gains --disable apps --disable plugins

A behaviour-changing default: the release brief must name the consumer who WILL
see a change, inverting our usual rule. Verify the flags exist on the pinned
codex version first — a bad flag makes codeCliResolves fail and silently
disables the `code` tool entirely, which is worse than the hole.
D-11 · D-4 · D-5

Three small knobs

low risk
In plain terms

D-11: you can finally raise the step limit, which today is the one budget dial nobody can turn. D-4: a skill written with perfectly valid formatting becomes findable again — two were invisible for months. D-5: a newly added skill is found without restarting the daemon.

What is actually happening

Steps is the only budget axis the profile does not let an environment variable override. Skill descriptions are matched with a regex that captures the literal > from a YAML block scalar, leaving a description too short to ever match a search. And the skill index is built once in the constructor and never refreshed.

The change
profiles.ts:129  read DELTA_MAX_STEPS beside DELTA_MAX_TOKENS / _COST_USD
  floor at 1, not 0 — maxSteps:0 fails every run before step 1
local-skills.ts:37  accept > and | block scalars; warn under 10 chars
local-skills.ts:46  re-scan in search() behind an mtime check, never a watcher

Fleet scope check: max steps ever reached across 204 Aperture runs is 62 of
100, and 0 of 12 lanes ship a skills/ directory. These help Delos, not the fleet.

Proving it

The test battery, in the order it runs

Each tier gates the next. Nothing reaches npm until tier 4 is green.

  1. Tier 0 — unit, one per item, each verified to FAIL without its fix This is not ceremony: 0.2.12 kept two regression tests specifically because they were checked against the un-fixed code, and an earlier test had passed without its fix, which is how a defect shipped behind a green suite. Write the test, watch it fail, then write the fix. Then bun test whole-suite plus typecheck and lint.
  2. Tier 1 — smoke against a running server bash scripts/smoke.sh. Adds one new assertion this release: /v1/status returns the three tool lists and the counts reconcile against the configured allowlist.
  3. Tier 2 — Aperture lab lane, quick-search The regression tier. Run the same pinned job on 0.2.14 and 0.2.15 and compare, because every high-risk failure here is silent and only shows up as a number moving the wrong way.
  4. Tier 3 — Ferni on Telegram The only lane that exercises D-1 the way a human meets it, because Connect threads a whole conversation into one session. Also the only lane with local skills, so D-4 and D-5 are provable nowhere else.
  5. Tier 4 — Delos, D-12 only Delos owns the only lane on the Codex subscription, so it is the only place the headline provider fix can be confirmed at all. Require 3 of 3 children succeeding on a --from-source deploy.

Go / no-go

What must be green before npm

Four gates, and the release gate is not the test suite

  • Every tier-0 test verified to fail without its fix — not merely passing.
  • Aperture tier-2 shows no measure moving the wrong way, especially compaction count and post-compaction input tokens. A silent performance regression is the failure mode this release is most likely to produce.
  • Ferni tier-3 D-1 and D-2 pass by hand. The D-2 case — key returns without a restart — is the one that proves we did not break the vault flow.
  • Delos reports 3 of 3 children. We cannot run this ourselves; nobody else has the provider.

Then publish, redeploy without --from-source, and run the battery again against the published package. An agent left on a worktree build is running something nobody else can reproduce, and a release nobody has installed is untested.

Two things deliberately not in this release, so nobody looks for them: the partial-answer call on exhaustion (0.2.16, the only genuine behaviour change in the backlog) and the prompt-cache history digest (0.2.16, and it now starts with a targeted capture session because no lane has one recorded).
