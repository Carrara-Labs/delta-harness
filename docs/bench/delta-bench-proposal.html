Proving a release is better than the one before it.

L0

One change, three answers

Start with the thing that happened last week, because the whole design falls out of it.

During 0.2.12 I made one change to how the engine bounds tool-call arguments, ran it once against a control, and reported the result. Then I ran the identical change again.

Run 1 · reported −29.9% A big win. This is the number that went into a summary and nearly went into a changelog.
Run 2 · same change +22.9% Same code, same fixture, same model. The sign flipped.
Run 1 · re-examined +50% work The "cheap" arm had quietly done 18 writes where the control did 10. It looked cheap because it was throwing work away.

Three separate failures, and only one of them is about the number:

  1. One run against a nondeterministic model is not a measurement. Three runs of that same change produced 163k, 286k and 202k tokens on one fixture.
  2. The metric set was chosen after the result was seen, so it happened not to include the metric that would have caught the regression.
  3. The workload was invented by the person judging the result. I designed a fixture, so it measured what I expected it to measure.
The actual problem behind the problem

Delta Harness is a context-economics engine. 0.2.11 moved a production agent's cache hit rate from 11% to 91% and cut cost by a third at volume. Those are the changes that justify the project, and they are exactly the changes whose effect is invisible to a unit test and drowned in variance by a single live run.

We have 883 passing tests. Not one of them can tell you whether the next release is cheaper, faster, or better than the last. That is the gap.

What Delta Bench is, in one sentence

A benchmark rig that takes real runs your agents already did, replays them against two or more versions of the engine under identical conditions, and gives you one table with a quality gate, a cost delta, and a confidence interval — so "this release is an upgrade" becomes a claim you can check instead of a claim you make.

L1

The guard metrics are the point. duplicate_tool_calls and rework_ratio are in that list because they are what caught the 0.2.12 regression — after the fact. The rig fixes the metric set at plan time so a change can never again be judged by a scorecard drawn up once the result is known.

L2

Five stages

Everything the rig does is one of these. Nothing else lives in it.

01Ask Your bullets, matched to a playbook. The playbook carries the gate, the metric set and the fixture query. → plan.json
02Select Query agent_events for real runs matching the population. Freeze them as an immutable fixture set with a content hash. → fixtures/*.jsonl
03Run Every fixture × every arm × every repetition, on isolated ephemeral machines, from identical seeded state. → transcripts + events
04Score Gate first (deterministic checks, then a calibrated judge). Only what passes the gate is eligible for a cost comparison. → scores.jsonl
05Verdict Paired differences per fixture, standard errors, confidence intervals. Ship / hold / inconclusive, with the reason. → verdict.md + report.html

The rig itself stays thin, deliberately. It drives the daemon's public seam and reads the telemetry every agent already emits. No product API, no product database, no per-app adapter. That is what makes one rig work across Quick Search, Intake, Prep, Ferni and Brain without knowing anything about any of them.

What it talks to

Two surfaces, both already public and already stable: POST /v1/tasks to drive a turn, and the telemetry outbox to read what it cost. Both are part of the harness contract, so the bench needs no privileged access and no engine changes to work.

L3

Fixtures come from production, not from imagination

This is the one design decision everything else depends on, and it is the one I got wrong the first time.

A fixture I invent measures what I expect. A fixture drawn from a real run measures what actually happens — including the parts nobody thought to look for. We now have enough traffic that the interesting runs announce themselves, and they are already sitting in agent_events with their inputs, turn counts and outcomes.

Expensive

Top cost per run, or worst cost per delivered unit. Where an engine change pays for itself.

Long

Highest turn counts and wall-clock outliers. The only place compaction and cache decay are visible.

Repetitive

The user had to follow up many times — the honest signal that the agent did not finish the job.

Failed

context_irreducible, budget exhaustion, breaker latches, compaction storms.

A fixture is a frozen conversation, not a prompt

Replaying a real run means replaying its shape: the seeded workspace, the bundle in force at the time, the ordered user turns, and the tool surface that was connected. What it must not replay is the side effects. 

fixtures/ferni-2026-07-31-a91c4/
├── manifest.json      agent, bundle hash, model, route, turn count, why selected
├── seed/              workspace state at t=0, restored fresh for every single run
├── turns.jsonl        the ordered user inputs, verbatim
└── tools.json         tool surface + record/replay policy per tool
The honest limitation

Replay fidelity is a spectrum, not a guarantee. Read-only tools (search, fetch, an MCP knowledge-base read) replay perfectly from a recorded cassette. Tools with side effects — sending a message, writing to a client's system — must be stubbed, and a stub is a place where the replay stops being the real run.

The rig should state which tools were live, which were replayed, and which were stubbed, on the verdict. A result whose fixture stubbed half the tool surface deserves less of your confidence, and the report should say so rather than let you infer it.

L4

Four kinds of arm

An arm is anything you can point the same fixture at. The rig does not care which kind you pick, which is what lets one tool answer four different questions.

Engine

Version vs version

0.2.12 from npm against your worktree at HEAD. The release gate: is the next version actually an upgrade?

Bundle

Config vs config

Same engine, different DELTA.md, POLICY.md, model, effort level or tool surface. The question an operator has, and the one nobody can answer today.

Route

Token route vs token route

Identical engine and bundle, reached through Anthropic-native, OpenAI-native or OpenRouter. Cache economics differ per route — see L6.

Foreign

Delta vs another harness

The same fixture driven through OpenClaw, Pi or Hermes Agent behind a thin adapter. Honest comparison, with caveats — see L9.

Arms are declared, never inferred. An arm pins an engine source, a bundle hash, a model, a route and an effort level; anything unpinned is a confound, and the rig refuses to run a plan with an unpinned axis rather than quietly varying two things at once.

L6

The route axis: the same change is worth different amounts on different wires

Delta already speaks three wire formats. They do not merely price caching differently — they hand you a different lever, which means a context-management change can be a win on one route and a no-op on another. Any bench that reports a single cost number without naming the route is reporting a coincidence.

Anthropic-native api: "anthropic" · Messages API
  • Caching is explicit: you place cache_control breakpoints yourself
  • Writes cost a premium over base input; reads are discounted roughly ten-fold
  • Minimum cacheable prefix around 1,024 tokens; TTL is a choice (short or long)
Lever: breakpoint placement. This is the route where 0.2.11's fix lived — rolling breakpoints were landing on per-turn ephemeral blocks, so only the spine was ever re-read. Placement is a strategy you can get catastrophically wrong, and therefore one a bench can measurably improve.
OpenAI-native api: "responses" · incl. codex sign-in
  • Caching is automatic: no breakpoints, no control, no write premium
  • The system matches the longest stable prefix above a ~1,024-token threshold
  • Discount on cached reads is set by the provider, not by you
Lever: prefix stability only. Breakpoint work is worth exactly zero here. What pays is never mutating an early byte — which makes this the route that punishes compaction rewrites hardest, and the one where the Sphere finding bites: a context that shrinks versus the previous turn missed cache 16 times out of 16.
OpenRouter api: "openai" · default backup path
  • Behaviour is whatever the upstream provider does, and can change under you
  • Cost arrives in the usage chunk rather than being computed locally
  • Same model, different upstream, different cache semantics
Lever: none — this route is a measurement, not a control. Its value in the bench is as a fidelity check: if a change wins on the native routes but vanishes here, the win depended on control we do not have in the fallback path, and the fleet should know that before it fails over.

Why one number is not enough

Illustrative shape, not measured data — this figure states the hypothesis the route playbook exists to test. The point is structural: a change targeting breakpoint placement can only pay on the route that has breakpoints, and a bench that averages across routes will hide that.

What the rig needs from each route

RouteAuth in the rigCost sourceCache signal available

openai-native API key or the Codex subscription broker Computed locally; subscription runs are metered but unbilled Cached-token count only, no breakpoint control

A subscription arm needs its own accounting. Running an arm through the Codex sign-in path produces real tokens at zero marginal dollars, so a naive cost-per-run column would declare it the winner every time. The rig has to report subscription arms in tokens and turns, and mark the dollar column n/a — subscription rather than $0.00.

L7

Execution: ephemeral Fly Machines, one per cell

A plan of 12 fixtures × 2 arms × 5 repeats is 120 runs. Run sequentially on a laptop that is an overnight job with contaminated state; run as 120 short-lived machines it is about the wall-clock of the slowest single run, with perfect isolation.

Fan-out

Each cell is one machine: created from the arm's image, seeded with the fixture's workspace, driven through /v1/tasks, drained of telemetry, destroyed. Per-second billing means 120 short machines cost about what 120 sequential runs cost, but finish in a fraction of the wall clock — the trade we are making is concurrency, not money.

Why this is a natural fit rather than a clever hack

Delta already runs one agent per Machine in production, with a mounted volume for SQLite and workspace, a control plane that owns suspend and resume, and /healthz as the wake probe. A bench cell is the same shape with a shorter life. There is no second deployment model to build and no second thing to keep in sync.

Fidelity is a ladder, and the rig should say which rung it ran on

local Daemon on your box, real bundle, real model. Fastest loop; hides everything about the platform. seconds to start
lane · warm Real Fly Machine, already running. Real network, real volume, real region latency. ~1s to dispatch
lane · cold Machine started from suspended. The rung that catches what only appears on resume. seconds, then MCP discovery
lane · pinned Same region and volume as the production agent being modelled. Slowest, most faithful, release-gate only. provisioning
The rung that would have caught a real bug

A 300-second first-turn stall in Quick Search turned out to be a dead pooled socket after suspend-resume. No local run could ever have produced it, and no warm lane run either — it only exists on the cold rung. A rig that offers only the fast rung will tell you a release is fine and be wrong in the exact way that costs a client.

L8

Telemetry: nothing new to instrument

The reason this rig can be small is that the measurement layer already exists and is already running in production. The bench is a reader, not an instrumenter.

Every Delta daemon emits a structured event per happening, correlated on the spine user → agent → session/run → task → turn, into a local SQLite table that doubles as a durable outbox and ships as NDJSON to a collector. Setting DELTA_CAPTURE_PAYLOADS=1 adds full prompts and outputs — off in production by default, on in every bench cell, because a bench with no transcripts cannot grade anything.

The metric taxonomy, and why the tiers matter

Gate

Did it do the job? Read first. Fail here and no cost number is printed at all.

Primary

The thing the change is trying to move. Declared in the plan, one to three metrics.

Guard

What this class of change is known to break. A guard regression blocks a primary win.

Report

Context, never a decision input. Printed so a human can spot something nobody predicted.

Gate before cost is the single most important rule in the rig, because the failure it prevents is the one that actually happened. An arm that filed 4 of 10 pages as garbage looked 60% cheaper, and cheapness was the first thing I looked at. Under this ordering that arm never reaches a cost column — it is reported as a gate failure and the comparison stops there.

L9

Statistics: where the error bars come from

This is the part that turns a pile of runs into a decision, and it is the part I skipped. The methods below are standard for model evaluation; none of them are exotic, and all of them are cheap relative to the cost of shipping a regression.

Paired differences, because the pairing is free

Both arms run the same fixture. That means the right statistic is not "mean of A versus mean of B" but the mean of the per-fixture difference. Fixture-to-fixture variation — some runs are simply longer and pricier than others — cancels out entirely, and what is left is the effect of the change. Published work on model evals puts the correlation between arms on the same question between roughly 0.3 and 0.7; the variance reduction from pairing is substantial and costs nothing but bookkeeping.

Repetitions, because the model is nondeterministic

Each fixture runs k times per arm. The playbook sets k from how noisy that metric class is: structural counts settle in about three, latency needs seven or more. Where the question is "does it work every time" rather than "can it work", the statistic is pass^k — the probability all k succeed — not pass@k, because a production agent that succeeds one try in three is not a working agent.

Clustered standard errors, because fixtures are not independent

Five repetitions of one fixture are five correlated observations, not five independent ones. Treating them as independent shrinks the error bars fraudulently. Clustering the standard error at the fixture level is the correction, and it is what stops the rig from manufacturing confidence it has not earned.

Inconclusive is a first-class verdict — an honest "we need more runs to tell" is worth more than a confident number that flips sign on the next execution.

L9

Foreign arms: running the same fixture through another harness

We claim Delta is leaner and cheaper. Right now that claim rests on reading competitors' source, which is a good way to understand a design and a bad way to know a number.

A foreign arm is any runtime that can accept a task and return a transcript. The adapter contract is deliberately the smallest thing that could work — one function, the same shape the research-grade agent leaderboards converged on: 

type ForeignArm = {
  name: string
  setup(fixture): Promise<Handle>        // seed workspace, start runtime
  send(handle, turn): Promise<Transcript> // one user turn in, transcript out
  usage(handle): Promise<Usage>           // tokens, cached, cost, per call
  teardown(handle): Promise<void>
}

OpenClaw Gateway / headless CLI in its container Completion, turns, tokens, cost, cache read/write Tool surface differs; it carries a much larger built-in toolset

Fair comparison, or none

Cross-harness numbers are the easiest thing in this whole document to produce dishonestly. Three rules make them worth publishing: the fixture subset must be portable (no Delta-specific tools), the grader must be identical for every arm and blind to which arm produced the output, and capability gaps get declared, not scored as failures — if a harness cannot do a fixture at all, that is a footnote in the table, not a zero that flatters us.

Prior art, and an honest position

I went looking for who has already built this, partly for ideas and partly to find out whether it needs building. Both answers were informative, and one of them was uncomfortable.

What the competition already has

ahead of us

OpenClaw · qa-lab

A full lab: a scenario catalogue, a Docker harness, JSONL replay, runtime-vs-runtime parity, cache-miss diagnostics, a 551-line token-efficiency report, mock-versus-live provider modes and a lab server with a UI. This is the closest thing to Delta Bench that exists, and it is further along than I assumed.

partly

Pi · packages/evals

Behavioural model-backed evals over a real agent session in isolated temp dirs, with a baseline-versus-candidates table and repetition counts — genuine statistical intent. Fixtures are hand-written smoke scenarios; no cost or cache metrics.

partly

Hermes · batch_runner.py

Parallel batch execution over a JSONL dataset with multiprocessing, checkpointing and resume, trajectory capture and tool-usage aggregation. Built for training-data generation rather than release gating, but the fault-tolerance design is the right one to copy.

Outside the three, the research world has converged on shapes worth borrowing: the Holistic Agent Leaderboard validated a framework-agnostic harness across 21,730 rollouts on nine models and nine benchmarks for roughly $40,000, decoupling scaffold from benchmark behind a one-function interface and tracking cost at the API-call level. Inspect AI settled on a clean decomposition — dataset → task → solver → scorer — with sandboxed execution and a log viewer. Anthropic's own eval guidance supplies the discipline: capability suites separate from regression suites, grade the outcome and the transcript but not the path, calibrate a model judge against human labels before trusting it, and treat a 0% pass rate as a broken task until proven otherwise.

Why a consumer would install it

The engine is product-neutral; the bench should be too. An Aperture or Ferni operator has exactly the same question we do, one level up: did my DELTA.md edit make this agent better? Prompt, policy, model, effort and tool-surface changes deserve the same discipline as an engine change, and today nobody has any way to get it — they ship the edit and watch the bill.

Point bench at your own agent, let it pull your own worst runs, get a table. That closes the loop from "the engine is configurable" to "the configuration is tunable", which is a materially different product claim.

—

What it costs, and how it could go wrong

Money

Statistical rigour multiplies API spend. Twelve fixtures × two arms × five repeats is 120 real agent runs. Mitigation: the local rung for iteration, the lane rung for gates only; short fixtures for smoke, long ones for release; a hard budget ceiling in the plan that aborts rather than overruns.

Replay fidelity

Side-effecting tools must be stubbed, and time-dependent state drifts. A replay is a model of a run, not the run. Mitigation: declare live/replayed/stubbed per tool on the verdict, and never let a heavily-stubbed fixture carry a release gate alone.

Fixture staleness

Fixtures are frozen so results stay comparable, which means they slowly stop resembling what the product does now. Mitigation: date-stamp fixture sets, re-select each quarter, and keep the old set runnable so historical verdicts remain meaningful.

Judge drift

A model grader is itself a model, and it moves. Mitigation: pin the judge model and prompt as part of the plan, keep a small human-labelled calibration set, and re-check agreement whenever the judge is changed. An uncalibrated judge is a rumour.

Rig sprawl

OpenClaw's lab is roughly 250 files. That is the natural end state of a rig that keeps absorbing scope. Mitigation: the cookbook lives in data, not code — playbooks are plain files, so the rig gets smarter without the binary getting fatter.

Measuring the wrong thing well

A rig with beautiful statistics can still answer a question nobody asked. Mitigation: fixtures come from real complaints and real cost outliers, so the population is chosen by production rather than by whoever is writing the change.

How I would build it

Thin slice first, and the thin slice has to be immediately useful on the very next engine change — otherwise this becomes an infrastructure project that outlives its motivation.

There is an open engine question right now — whether eliding a tool call's arguments once it is N turns old beats both seams already tried — and it has three existing arms to compare against. Building M0 to answer that question is how the rig gets specified by real use instead of by design, which is the only way I trust it to end up lean.

Delta Bench — design proposal, 2026-08-07. Nothing here is built. Written so the next person does not re-derive it, and so the small tests run in the meantime are shaped to feed it.
