The rule that governs all of it

Every fix ships with a test that fails without it

This is not a formality here. In 0.2.12 two regression tests were kept specifically because they were verified to fail without their fix — and one earlier test had passed without its fix, which is how a defect shipped behind a green suite. So the instruction to whoever implements is: write the test, watch it fail, then write the fix.

Three of the tests are doing more than proving a fix. They lock a decision:

D-2 — insert EXA_API_KEY into the vault and re-request /v1/status without restarting; assert web_search is no longer unusable. This test fails under the fix the field report proposed, which is the point of writing it: de-registering credential-gated tools at boot would break the runtime credential flow we shipped in Connect 0.4.3.

D-7 — a message row carrying a legacy spill path must still demote after the scratch root moves. Without this, relocating the root silently stops the retained tail from shrinking, which is the exact defect 0.2.11 was written to fix, presenting as a performance regression with no error.

D-1 — a single-request session's summary must be byte-identical before and after. That is the property that makes the change shippable as a patch rather than a behaviour change.

Plus the standing gate before anything is called done: bun test and bash scripts/smoke.sh against a running server.

Before npm

The two things the release gate actually requires

  1. Deploy from source to a real agent and finish the human test me + you sh connect/deploy/deploy.sh --from-source builds from the worktree, so the deploy → test → fix loop needs no release. D‑12 is the one that cannot be verified here — Delos owns the only lane with that provider. Their reproduction is already written: one /v1/responses call asking for a single research with three tasks, reporting verbatim whether each child succeeded. Require 3 of 3 before publishing. A fix to a wire format nobody exercised is a fix we do not have.
  2. Publish, then redeploy without --from-source me And run the post-release battery against the published tarball rather than the repo. An agent left on a worktree is running something nobody else can reproduce, and a release nobody has installed is untested. npm is a permanent public trail — a mistake is cleaned up with npm deprecate, never unpublish.

Open

Five questions the reviewers must answer

Written into the specs rather than decided quietly, because each one could reasonably go the other way.

  1. D-1: should the seq-1 fallback exist at all? The spec argues for deleting it — 42 of 42 measured pins under that query were the wrong task, so a fallback whose behaviour is the bug is not a safety net. No pin degrades; the wrong pin corrupts.
  2. D-9: does the handoff belong in the transcript? finalize inserts the output as an assistant message on any non-done status, so it enters the next turn's context automatically. Good for resume; also new context on a session that just proved it was over budget. The most consequential open question in the release.
  3. D-7: fallback forever, or refuse to boot on a changed root? Falling back is simpler and permanently carries two path candidates. Refusing is safer for a fleet and makes the operator choose. The spec picks fallback and says the other is defensible.
  4. D-3: return shape or callback? builtinTools has exactly one caller, so the honest return-shape change is cheap. Confirm that caller count independently, including tests.
  5. Semver, finally. 0.2.15 is additive, like 0.2.7 through 0.2.14. version.ts documents additive = MINOR. Either the doc moves or the practice does — a fifth release either way makes it worse.
