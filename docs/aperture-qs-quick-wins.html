Tuning Quick Search

Three settings we can change today, with no code and no release, measured against 140 real runs of this exact lane. Then what 0.2.15 adds, and the two things we should deliberately not touch before a demo.

7% of model calls are consuming 31% of the spend, and one unused setting reclaims 41% of the bytes that cause it.

Everything below comes from the lane itself — aperture-qs-69598a208017, 140 runs, 2,718 model calls, $669 of measured spend. Not from the docs, and not from another lane.

One thing to rule out immediately: the tools are not the bottleneck. Making fiber_read faster would be invisible. Making the prompt smaller would not.

The finding

Where the money actually goes

Not spread evenly. Concentrated in one moment, repeated 192 times.

In plain terms. When the conversation gets too long, the agent stops and rewrites its own history into a summary to make room. The very next thing it does is re-send that whole rewritten history to the model — and because it changed, none of it is cached any more. So it pays full price for about 227,000 tokens, in one call, and that single call costs roughly seven times what a normal one does.

Technically. Compaction rewrites the prefix, which invalidates the prompt cache from the first changed block onward. The reload is structural rather than a bug: any prefix rewrite costs one full re-cache. It is not something to fix in compaction; it is something to trigger less often.

Ship today

Three settings, no code, no release

All three already exist in 0.2.14, which the lane is already running. Each is one environment variable and a restart.

WIN 1

Stop replaying long tool arguments on every turn

biggest win
In plain terms

When the agent writes a long report body, it sends that text as an argument to a tool — and that text then rides along in every single subsequent message for the rest of the run. Nothing ever trims it. On this lane the model wrote arguments averaging 11.8 KB, the largest 47.7 KB, and re-sent them again and again. There is a setting to cap that which was built for Aperture, shipped in 0.2.12, and never switched on.

What is actually happening

Every large thing entering context passes a bounding rail — tool results get capped and spilled to disk, retrieval blocks get capped, the self-file gets capped. Assistant tool-call arguments had none, in either direction, because the shrinking pass opens with if (m.role !== "tool") return. 0.2.12 added the rail and shipped it opt-in for one cycle, deliberately, because its echo guard was new. That cycle has passed and nobody turned it on.

The change, and what it is worth here
DELTA_TOOL_ARG_MAX_BYTES=4096  (config.ts:230, default 0 = OFF)

measured on this lane's journal, 4,899 calls:
  total stored argument bytes     4.83 MB
  reclaimable at a 4 KB cap      1.99 MB  (41%)

  aperture__qs_stage_body  206 calls  avg 11,831 B  → 1.61 MB reclaimed
  remember                80 calls  avg  7,621 B  →   282 KB
  aperture__qs_save_artifact  82 calls  →    77 KB

elision happens at the COMPACTION commit, not at write time — so it costs no
extra cache churn, and the full arguments stay in `journal` for recall.
Risk, and how we would know

Known cost: the guard that stops the model imitating the elision marker adds roughly 8 extra model calls on a long filing session. That is the reason it shipped opt-in. Watch: compaction count per run should fall, not rise; if the agent starts re-writing work it already did, turn it off. The reference build measured 5 compactions going to 0, input tokens −29.9%, and cost −36.5% on the same job.

WIN 2

Keep the cache warm for an hour instead of five minutes

free, already proven on Ferni
In plain terms

The provider keeps a cached copy of the conversation so repeat work is cheap and fast. By default it expires after five minutes. Ferni has been running the one-hour setting for weeks; the Quick Search lanes never got it. The first call of every run currently lands at 21% cache hit — it is paying to re-read work it did minutes earlier.

What is actually happening

DELTA_CACHE_TTL=1h attaches a one-hour retention to the stable cache breakpoints. Cache writes bill at 1.25× input, so it costs a small premium on the first turn and repays it on every read afterwards. On this lane reads dominate overwhelmingly — 2,105 calls sit in the sub-one-minute band at 91% hit — so the premium is easily covered.

The change
DELTA_CACHE_TTL=1h  (config.ts:197 — the literal string "1h" is the only accepted value)

what it targets on this lane:
  first call of a run     140 calls  21% hit  $60.41

Risk

Low, and it is the one change already running in production elsewhere. The only downside case is a lane that writes cache and never reads it back, which is the opposite of this lane's profile.

WIN 3

Let the agent finish writing down what it learns

stops wasted turns
In plain terms

The agent keeps a small self-file of things it has learned. On this lane that file is full, so writes to it are being refused — around a hundred times. Every refusal is a turn the agent spent, paid for, and got nothing from, and it also means the lane has silently stopped learning anything new.

What is actually happening

DELTA_SELF_MAX_TOKENS=2400 on this lane, against 4000 on the intake lanes and 1600 on two others — three different values across one fleet, none of them chosen for this workload. Self-file fullness turned out to be the single best predictor of degraded self-learning across the fleet, which is why 0.2.12 put it on /v1/status.

The change
DELTA_SELF_MAX_TOKENS=4000  (matching the intake lanes)

on this lane, from the transcript:
  self-write refusals           ~125  (42% of ALL tool errors)
  write collisions between runs   23
  `remember` calls attempted      170

check the current figure first: GET /v1/status → `self` reports live fullness.
Risk

A larger self-file means a slightly larger cached prefix. It sits in the stable part of the prompt, so it is cache-read at the cheap rate rather than re-billed. Note this is a different fix from the 23 collisions, which are two runs writing at once and are ours to fix in 0.2.16.

Do not touch

Two tempting changes to leave alone

Do not drop reasoning effort to low before this demo

It is the most tempting dial on the board: our own effort lab measured −56% p50 latency and half the cost at low, with blind quality inside the margin. But that measurement was taken on chat-shaped work, and Quick Search is research-shaped — multi-step, evidence-gathering, exactly the profile most likely to degrade when you cut reasoning. Changing it a few days before the highest-stakes demo we have had, on the axis we have not measured for this workload, trades a visible risk for an invisible one. Test it after, properly, with their bench rig.

Do not raise the compaction threshold

DELTA_COMPACT_AT_TOKENS=200000 looks like an easy way to compact less often, and compacting less often is exactly what we want. But the usable ceiling for claude-opus-5 is its window minus the output reserve — 249,000 − 40,000 = 209,000. There is about 9,000 tokens of headroom, which buys nothing, and going past it trades a cache miss for a hard overflow. Win 1 reduces compaction the right way, by putting less in.

Order of operations

What I would do, in order

  1. Check the live numbers first Everything above is the 0.2.11 snapshot; the lane has been on 0.2.14 since 10 August, and 0.2.13 already decoupled the retained tail from the trigger. Re-run the post-compaction query against the live lane before assuming the $205 line is still that size. It will be smaller. It will not be gone.
  2. Set all three variables, restart, run one pinned job They are independent, so they can go together. Compare against the same job on the current settings.
  3. Look at exactly four numbers Compactions per run, post-compaction input_tokens, cost per run, and wall clock. Win 1 should move all four down. If compactions go up, revert it — that is the only signal that matters.
  4. Then ship 0.2.15 behind it D-1 removes the wrong-question failure, which is the one that would actually embarrass us in front of a lab founder.

All three settings are reversible by removing an environment variable and restarting. None of them touches code, none is in the 0.2.15 diff, and none can regress a build that is already deployed across twelve lanes.
