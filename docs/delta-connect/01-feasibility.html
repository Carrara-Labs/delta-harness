Feasibility assessment · Dogfooding Delta

Chatting with your own Delta agent

Run a Delta agent on the Mac Mini, talk to it from Telegram, and lean on it every day to feel out its strengths and weaknesses. Four probes swept the harness, the control plane, and the reference agents. Here is everything they found.

Feasible Small lift The tension dissolves

Bottom line. The full chat loop already lives at Delta's HTTP seam - you build a thin shim, not an engine. On an always-on Mac Mini the daemon idles at ~30MB, so the "agent is off, chat wants it on" worry never bites. A working chat UI even exists already inside the control plane. The realistic starting point is a single-file Telegram bot: roughly half a day to something you use daily.

01 · The architecture question

The tension you named - and why it dissolves

Delta's signature trait is scale-to-zero: an agent can be switched fully off and woken on demand. A live chat, by contrast, wants something listening at all times. That looks like a conflict. It is not.

The always-on piece is a dumb socket-holder, not the intelligence. That is a cleaner split than Hermes or OpenClaw, which fuse the socket and the agent into one always-on process. And on a Mac Mini you can sidestep the whole question: keep the daemon running at ~30MB and skip scale-to-zero entirely - it is a cloud-cost trick you do not need on hardware you already leave on.

02 · What the probes found

Most of the machinery already exists

Across three repositories, the picture is consistent: the hard parts (durable sessions, a clean request/reply seam, a turn engine, even a chat UI) are built. What is missing is small and predictable.

delta-harness

The engine

The in-VM agent loop. Ships no channel code on purpose.
  • ✓Sync request/reply seam. POST /v1/responses → output_text. One call in, one reply out.
  • ✓Durable sessions thread via previous_response_id and survive off/on cycles.
  • ✓Suspend-safety + auth. /v1/busy signal, bearer token, per-session ownership.
  • +Nothing in the engine. Channels are an explicit non-goal - correctly so.
delta-agents

The control plane

Provisions and hosts agents on Fly microVMs from Railway.
  • ✓A chat UI already exists. Dashboard has text box, send, poll-for-reply, threads, plan cards.
  • ✓Robust turn engine with per-user FIFO, background runs, memory threading.
  • ✓Suspend / resume primitives - warm resume clocked at ~2.7s.
  • +Wake-on-message. Today a suspended agent returns 409; swap that for a resume().
  • +Auto-suspend on idle. A small post-turn ticker. Both use functions that exist.
.refs

Reference agents

Hermes, OpenClaw, Pi - studied for the proven pattern.
  • ✓Two converge on one shape. A long-poll listener → session map → call agent → post reply.
  • ✓Long-poll needs no public URL. Just outbound HTTPS - ideal for a home box behind NAT.
  • ✓The relay split (Hermes) is the escape hatch if you ever want the agent to scale to zero.
  • +Pi skips chat entirely - useful only as a supervisor/lifecycle reference.

03 · The recommended architecture

The five-part chat loop

Both Hermes and OpenClaw reduce to the same seam. For Delta on the Mac Mini it is a single always-on file in front of the local daemon. This is the whole thing.

1

You message the bot from your phone

A Telegram bot you create with @BotFather. Nothing else on the phone side.

requires: TELEGRAM_BOT_TOKEN
2

The shim pulls updates by long-poll

One resident process runs getUpdates via a maintained SDK (grammY). No public URL, no TLS, no webhook - just outbound HTTPS from the Mac Mini.

the only always-on component
3

It maps your chat to a Delta session

A tiny table: chat_id → last resp_id. Handing the same id back each turn is what gives the conversation continuity across messages - and across restarts.

key: telegram:{chat_type}:{chat_id}
4

It calls the local daemon

A single HTTP POST to the Delta agent running on loopback. The daemon wakes if needed, runs the turn against durable state, and returns the answer.

POST localhost/v1/responses → { output_text }
5

It posts the reply back to you

Simplest: send the final text. Nicer later: one placeholder message, then edit it as tokens stream - Hermes' universal edit-transport, which works the same on Telegram, Slack, and Discord.

optional hardening: allowlist your own chat_id

The recommendation

Start with the local Telegram shim on the Mac Mini.

It is the smallest new surface, has no production risk, needs no webhook or NAT gymnastics, and the always-on Mac makes the scale-to-zero question moot for v1. It gives you real, ambient, day-to-day dogfooding the fastest. The control-plane chat UI is already there as the complement whenever you want to inspect a run in depth. If you later want the agent itself to scale to zero, graft on Hermes' relay split - the shim becomes the tiny always-on connector and the agent sleeps between messages.

05 · Decide later, not now

Two open threads

Proactive messages

Should the agent ping you unprompted?

v1 just relays replies. If you later want the agent to message you on its own (reminders, nudges), wire a Telegram-send capability as an MCP tool, or fire it from a timer in the shim. The built-in schedule_self path needs a control-plane callback the shim can play.

Slack

Skip it for v1.

Slack's Events API wants a public webhook URL - more setup for a home box. Telegram long-poll is strictly easier. The existing Slack code in the control plane is outbound-only and approval-gated anyway, not a two-way chat channel.
