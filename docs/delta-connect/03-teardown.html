Design teardown · Delta Connect · v2

The competition is one machine. We win by unbundling it.

Fresh reads of Hermes and OpenClaw at today's HEAD, torn down against our own stack and the harness doctrine, then hardened by an adversarial codex review. The question was how to do the channel layer leaner, simpler, more powerful, and differentiating. The answer is architectural.

The thesis

Hermes and OpenClaw are the same shape: a resident, always-on daemon that welds the channel socket to the agent and keeps session state in RAM. Because the agent holds the socket, it can never sleep. Delta unbundles the two: a thin, always-on edge holds the socket and a minimal durable inbox/outbox; the agent sleeps behind it and wakes on message. The socket and the RAM state come off the agent. What we do NOT delete is durable messaging - that boundary is what makes sleep safe.

↺ Hardened by adversarial review - three first-draft claims retired

  • ✕"One lease row gives at-most-once." A lease is leader election, not at-most-once. Use durable occurrence rows.

01 · The premise, and its cost

Move the socket off the agent, keep a small durable core

Welding the socket to the agent is what forces the always-on process. Move the socket to a thin edge and the agent can sleep. But a minimal durable inbox and outbox stay - deleting those loses or duplicates messages, and that is not resident-process bloat, it is correctness.

03 · The verdict

What we steal, what we delete

Their good ideas are all contract-shaped and small. Everything that hurts is mechanism that metastasized past a contract. We take the first and refuse the second - keeping a minimal durable core codex was right to insist on.

Steal - the good, small ideas
Each is a boundary, not a subsystem.
Unbundle the socket from the agent Hermes relay
The connector holds the socket, the credentials, and a durable buffer; the agent dials nothing and holds no tokens. This one move gives NAT'd inbound, shared-token multi-tenancy, and scale-to-zero. Their code around it is heavy; the boundary is right.
Emit transport-neutral, render at the edge Hermes
The agent emits structured output, the edge decides delivery, events never carry context. Needs one new engine affordance (a final-answer marker) before we stream, since today's SSE deltas can cover intermediate tool turns.
Small per-channel codec + lazy load Hermes
verify / parse / render / send + capabilities. SDK imported only when the channel is used. One small file, no catalog, no facade shims.
The draft-stream loop OpenClaw
Single-flight, newest-wins, throttled edit-in-place. ~150 correct lines - but it ships LAST, after the engine marks final output. Not copied over a raw delta stream.
Supervisor mechanics OpenClaw
Reserve the abort handle before the first await, crash-loop breaker, bounded stop, external health watchdog. Steal the supervisor, not the plugin catalog.
Durable occurrence, run owns its outcome Both
A row keyed (schedule_id, scheduled_for) gives effectively-once admission and missed-run catch-up. NOT at-most-once from a bare lease. We already have the shape in event_deliveries.
Delete - the premise-driven bloat
The sprawl goes; the small durable core stays.
✕ Mirror dual-queue sprawl + 9-phase relay Both
→ one small inbox + one small outbox; inbound retries on a 5xx, outbound owns its own idempotent retry
✕ Resident socket per channel Both
→ webhook in, wake on POST - the thing that unlocks scale-to-zero
✕ In-memory cron map OpenClaw
→ durable occurrence rows, safe across suspend and instances
✕ In-RAM session ownership + reply fence Both
→ ownership in SQLite; the edge stays stateless per request
✕ Fat base + facade files + plugin catalog Both
→ small composable helpers; one small codec per channel
✕ Escape hatches in the agent contract Hermes
→ typed neutral fields to the agent; a raw ref kept inside the edge for debug
✕ A parallel turn engine Both
→ reuse the control plane's turn.ts as the single threading authority

04 · We are not starting from zero

The gateway middle already exists in our stack

Both competitors built a resident turn engine, a session-key scheme, a credential store, and a durable queue. We have all four already, in the control plane, with the correct designs. Delta Connect is a thin channel-adapter layer in front of them, not a rebuild.

The control-plane doctrine forces the split, and it is a feature: Telegram caps 20 bots per account, so the hosted fleet cannot give each agent its own bot. Both shapes run the identical codec and durable core; only the ingress driver differs.

06 · The payoff

Always on, yet scaled to zero - on Fly AND a Mac Mini

This is the split neither competitor can make. The gateway is always on and cheap; the agent sleeps behind it. Only the wake mechanism differs between substrates, and it hides behind one small interface.

  maybeSuspend(agentId): Promise<void>       // after a turn, iff /v1/busy is false

Why it is lossless on both: the durable inbox returns 2xx to the platform before the agent is guaranteed up, so cold-start latency never drops a message. From the user's side the agent is always reachable; from the cost side the heavy part sleeps. Hermes and OpenClaw weld those together and can never split them. Delta Connect is the seam that does, and the seam does not care whether it is fronting Fly or a laptop.

07 · Your eight questions

Why this is the better answer

Leaner?
The socket, catalog, fat base, in-RAM cron map, and 9-phase relay all go. What stays is one small inbox + one small outbox, far below their dual-queue sprawl.
Simpler?
One channel is one small codec. Ingress and durability are shared, not re-forked per platform. No two-manifest split, no facade files, no codegen.
More elegant?
Three clean seams: codec, ingress driver, durable core. The agent emits neutral output; the edge renders per platform.
More useful?
Bidirectional - proactive rides the same outbox as a reply. One codec serves a local bot and a hosted fleet.
More powerful?
Always-on yet scaled-to-zero on Fly and a Mac Mini behind one supervisor. NAT'd inbound and shared-token multi-tenancy come free with the unbundling.
Smarter?
We reuse the turn engine and durable queue we already run as the single authority, instead of building a parallel stack that can drift.
Better design?
A thin edge in front of an existing engine, with correctness boundaries (inbox, outbox, occurrence rows) made explicit, not emergent.
Differentiating?
They are the channel layer welded to the agent and can never sleep. Delta is a pure engine with an optional thin edge that scales to zero.

08 · Positioning & language

Not in the engine. Not a plugin catalog.

You asked whether this is an extension that makes Delta OpenClaw-capable, and how to talk about it. The words decide what leaks into the lean core.

In the engine?
No. The doctrine - "NOT building: channels", zero deps, <10ms cold start - is the moat. Channels in the engine is how you become OpenClaw, the thing we replaced.
Separate?
Yes - a separate package, @carrara-labs/delta-connect, same workspace, sharing only a tiny neutral-envelope + codec contract module with the engine.
Separate repo?
Not yet. A separate package keeps the shared contract ergonomic; a separate repo is premature until it grows its own contributors.
The word "plugin"?
Avoid it. Say connectors and edge. "Plugin catalog" is OpenClaw's framing and it drags in the registry, the manifests, and the ceremony we are deleting.
"OpenClaw-capable"?
Reframe. You get OpenClaw's reach without OpenClaw's weight - every channel, none of the resident-process tax - plus scale-to-zero it structurally cannot have.
The framing sentence

Hermes and OpenClaw are the channel layer, welded to the agent. Delta is the agent; Connect is an optional, thin edge.

The same connector runs from a single-file local bot on your Mac Mini to a shared multi-tenant gateway in front of a sleeping fleet on Fly. Hot-wire a Delta agent into anything, and it still scales to zero when the conversation stops.

09 · The build

Correctness boundaries first, then the polish

Codex reordered this: the loss and duplicate boundaries come first. Streaming and scheduling sit on top of them, so shipping the pretty draft loop first would bake the loss window in.

Build in this order
The durable spine before the shine.
  1. Durable spine - inbox + dedup by eventId, deterministic conversation ownership, async dispatch, durable outbox with idempotent send.
  2. Telegram codec + ingress driver - webhook (verified) for zero, long-poll for local. DM-only.
  3. Supervisor impls - Fly (start/suspend) and local (keep-alive). Close the /v1/busy suspend race.
  4. Outbound delivery + notify tool - final answer send with retry + flood control; proactive.
  5. Scheduling - durable occurrence rows; reuse event_deliveries.
Then, last: the streaming draft loop - once the engine exposes a final-answer phase, since SSE deltas can cover intermediate tool turns.
Refuse by design
What they built that we will not.
  • ✕Mirror dual-queue sprawl & 9-phase relay - one small inbox + outbox
  • ✕Plugin catalog, two manifests, facade files - one codec
  • ✕Fat base class & per-channel god-adapter - small helpers
  • ✕In-memory cron map & reply fence - durable rows
  • ✕Resident socket per channel in the default - webhook first
  • ✕Group chat in v1 - single-owner sessions; DM-only until actor split
The one line that keeps it lean

Both codebases prove the same law: the good ideas are contract-shaped and small; everything that hurts is mechanism that outgrew its contract. Hermes had a clean relay boundary and let it rot into 9 phases and a 1,656-line god-adapter. OpenClaw had a clean supervisor and buried it under a plugin catalog and two durable queues.

So: one channel at a time, webhook-first so scale-to-zero stays real, the codec stays small, the correctness boundaries stay explicit, and the edge never grows a god-adapter. The contract is free. The framework is what costs you.
