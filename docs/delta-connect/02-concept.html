Working name · Delta Connect

Give your agents a way in - and a way to reach back out

The harness left one space empty on purpose. This is the thin, reusable layer that fills it: normalize any inbound event into a Delta turn, then route the reply (or an unprompted nudge) back to whatever channel the person lives on. Telegram is the first adapter, not the point.

The one idea

It is not a Telegram bot. It is an agent I/O bus - the switchboard between the world's channels and events and a request/reply agent daemon. Every serious agent deployment quietly rebuilds this. Delta deliberately refuses to ship it inside the engine. That refusal is exactly what creates the reusable gap.

01 · The picture

One hub, both directions

Sources push events in; the hub normalizes them, remembers who is who, and hands the agent a clean turn. Replies and proactive nudges flow back out the same way. The agent never learns what a chat_id is.

The gateway is the only always-on part, and it is deliberately dumb: it holds sockets and moves bytes. All the intelligence stays in the agent, which can sleep between turns or run forever - the hub does not care. Inbound and outbound share one contract, which is what makes proactive messages (agent pings you first) fall out for free instead of being a second system.

02 · Where it sits

A layer, not a fork of the harness

It does not replace the engine and it is not scope-creep on it. It fills the space Delta's own doctrine leaves for someone else, across the seam Delta already drew.

L1 · Channels
Telegram, Slack, email, web, SMS, webhooks. The world, and the events in it.
L2 · Delta Connect
The always-on piping. Normalizes inbound into turns, routes outbound to channels, owns the identity map and channel credentials. The new thing.
L3 · Delta harness
The agent runtime. Thin, zero-dep, product-neutral, on/off-able. Unchanged.
L4 · Memory & tools
MCP, local memory, skills, code. What the agent composes to actually do things.

03 · What is inside it

Six small parts, one tiny contract

adapters

Channel adapters

One small file per channel. The SDK does the hard part (long-poll, retries). A plain in-code map, not a plugin framework.

normalize

The normalizer

Turns any inbound shape into { text, identity, sessionKey, attachments }. This is the seam everything else hangs off.

identity

Identity resolution

Maps a channel-native handle to one canonical user_id so Delta's session-ownership stays safe across channels and people.

sessions

Session store

A tiny durable table: identity → last resp_id. Hands the same id back each turn for continuity across messages and restarts.

router

Outbound router

A send({ identity, text }) endpoint. The agent (or a timer) says "tell Nic X"; the router knows what "Nic on Telegram" means.

custody

Credential custody

Bot tokens and channel keys live here, never in the agent. One place to rotate, allowlist, and gate who may talk to whom.

the entire reusable surface, roughly
// one adapter implements this. that is the whole contract.
interface ChannelAdapter {
  name: string
  listen(onMessage): void     // inbound: push normalized events
  deliver(target, text): void  // outbound: reply or proactive
}

type Inbound = {
  text: string
  identity: string     // -> canonical user_id (ownership)
  sessionKey: string   // -> previous_response_id (continuity)
  attachments?: File[]
}
Add a channel by writing one adapter against this. Nothing upstream changes. That is the difference between a leverageable tool and a pile of bespoke bots.

05 · How to package it

Separate package - not the engine, not a whole repo

Your instinct to reuse it is right, and the packaging is what protects it. Three options, one clear pick.

✕ No
in the engine

Inside @carrara-labs/delta-harness

Batteries-included, one install. But it breaks the three things that make the engine valuable:

  • Drags channel SDKs (grammY, Slack) into a zero-runtime-dep binary.
  • Bloats the <2k spine and the <10ms cold start the whole design protects.
  • Directly violates the stated doctrine: "NOT building: channels." Hard no.
✓ Pick
separate package

@carrara-labs/delta-connect, same workspace

Its own package with its own deps and release cadence, living beside the engine so it can share the normalization types.

  • Engine stays pure; users opt in only when they want channels.
  • The boundary already exists - it talks to the engine over the public HTTP seam, so nothing is forced.
  • Shared contract, coordinated evolution, minimal release overhead.
~ Too much
separate repo

A fully independent repository

Maximal independence, but premature. You lose the shared-contract ergonomics and have to sync two histories to co-evolve one seam. Revisit only if it grows its own team or external contributors.

Two homes, one contract: the standalone package serves the OSS self-hoster running a local daemon; the delta-agents control plane grows an inbound receiver implementing the same contract for hosted agents. Write the seam once, deploy it twice.

06 · What else to build

Roadmap with a spine of discipline

There is a real roadmap here, but the whole thing only works if the first build stays small and each later piece is pulled by real use, never pushed on spec.

Build first
This week. The thing you use daily.
  • 1Gateway core - normalizer, session store, dispatch.
  • 2Telegram adapter - long-poll, no public URL.
  • 3Identity map - handle → canonical user_id.
  • 4Outbound + notify tool - proactive from day one.
  • 5Allowlist - only you can talk to it.
Pull by demand
When real usage asks for it.
  • +Second adapter - Slack or email, whichever you reach for.
  • +Attachments - inbound files → /v1/files.
  • +Scheduler bridge - schedule_self → timed sends.
  • +Contacts directory - people ↔ their handles.
  • +Streaming replies - placeholder then edit-in-place.
Later / maybe
Only with a concrete reason.
  • ·Approval hook - human-in-loop outbound (control plane has one).
  • ·Admin / observability - conversations, delivery status.
  • ·More channels - Discord, WhatsApp, voice.
  • ·Agent-to-agent fabric - once two agents actually need it.
The line that keeps it from becoming overbuilding

Hermes ships adapters for Signal, iMessage, WhatsApp, WeChat, QQ, Teams plus a plugin registry and relay transports. OpenClaw has ~25 platforms, each a plugin.json. That is precisely the mega-gateway Delta deliberately walked away from. If you set out to build "the universal channel gateway," you spend two weeks on an adapter framework and never dogfood the agent.

The discipline: contract-first, one channel at a time, separate package, no registry. The seam is free - naming the interface cleanly costs nothing. The framework is expensive and premature. Build Telegram, use it for two weeks, and let the second adapter earn its place.
