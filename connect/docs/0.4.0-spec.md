# Connect 0.4.0 — Secure secret intake

Status: DRAFT for codex review · security-critical release, ships alone
Needs: Harness 0.2.10 (the Secret Vault) RELEASED — Connect writes `PUT /v1/secrets/:name`
over the loopback seam. Pin min-compatible harness 0.2.10.

## Intent — the novel piece

Neither OpenClaw nor Hermes can take a credential FROM the user IN the chat safely:
OpenClaw provisions secrets operator-side (env/file/vault CLI); pasting a key into
Telegram text parks it on Telegram's servers forever. Our move:

1. Agent (or user) decides a secret is needed → Connect sends a message with an
   **inline keyboard button (`web_app` type)** — "Provide EXA_API_KEY".
2. Tapping it renders OUR form **inside Telegram** (native sheet, no external browser),
   served from Connect's new public HTTPS endpoint.
3. The form POSTs the value **directly to Connect** over TLS via `fetch` — explicitly
   NOT `sendData()`, which routes through Telegram's servers as a service message.
   Telegram never carries the value; only our pipe does.
4. Connect authenticates the POST with the Web App's **`initData`**: HMAC-SHA-256
   verification (secret key = HMAC_SHA256(bot_token, key="WebAppData")), `auth_date`
   freshness, and the user id must be in `ALLOWED_TELEGRAM_USER_IDS` AND match the
   single-use intake session the button minted.
5. Connect writes the value to the harness vault (`PUT /v1/secrets/:name`, loopback
   seam) and confirms in chat by NAME only. The value is never logged, never stored in
   Connect's DB, never echoed.

Security equivalence: this is a one-time secure drop-box, cryptographically bound to
(bot, user, intake session), rendered natively in the chat. The webview is real
security — the direct-POST is what makes it so.

## Surface

### 1. New public HTTPS endpoint (the ONLY public route)

- Fly `[http_service]` added to the deploy (edge TLS on `<app>.fly.dev`), forwarding to
  a new Connect listener (`CONNECT_PUBLIC_PORT`). The daemon seam stays loopback-bound;
  nothing else is exposed.
- Routes (everything else → 404, no body):
  - `GET /intake/:sessionId` → the form page (inline HTML+JS, self-contained, no CDN).
    Serves only while the session is live (unexpired, unused); else a dead-session page.
  - `POST /intake/:sessionId` → `{initData, value}`. Validates (below) → vault PUT →
    marks session used → `{ok}`. The Mini App then calls `Telegram.WebApp.close()`.
- Public base URL config: `CONNECT_PUBLIC_URL` (e.g. `https://ferni-delta-connect.fly.dev`).
  Both set → intake enabled; absent → feature off, zero new surface (fail-safe).

### 2. Intake sessions (single-use, TTL)

- Minted when the button is sent: `{sessionId (uuid), name, purpose, telegramUserId,
  chatId, createdAt, usedAt}` in Connect's SQLite. TTL 15 min, single-use, sweep on
  access. sessionId is the capability: unguessable, short-lived, bound to one user+name.

### 3. POST validation (all must hold, constant-time where it matters)

1. Session exists, unexpired, unused.
2. `initData` hash verifies against the bot token (data-check-string per Telegram docs;
   exclude `hash`/`signature`; sort fields; LF-joined; hex HMAC compare, timing-safe).
3. `auth_date` within freshness window (300s) — initData is minted at Mini App OPEN.
4. `initData.user.id` == session.telegramUserId (and ∈ allowed users).
5. Value sane: non-empty, ≤ 4 KB, no control chars.

Failures → generic 403/410, no detail; log an event with session id + reason,
NEVER the value or initData.

### 4. Chat UX

- Trigger: the agent asks for a secret in prose + a marker convention
  `[[secret-request: NAME | purpose]]` in its reply (same family as `[[send: path]]`).
  Connect strips the marker and attaches the web_app button. Operators can also
  `/secret NAME purpose` to mint a button directly.
- On success: Connect posts "✅ EXA_API_KEY saved to the vault" (name only) and
  nudges the agent with a system-style turn so it can continue the task.
- `/secrets` command: lists vault names+purpose via `GET /v1/secrets` (no values).

## Non-goals

- One-time signed external link fallback (C0.5.0 — nearly free later, extra bearer-leak
  surface now).
- Any read-back of values, any Connect-side persistence of values.
- Non-Telegram channels (the pattern generalizes; Telegram is the shipped edge).

## Tests

- initData validation vectors (constructed with a test bot token): valid, tampered hash,
  stale auth_date, wrong user, missing user.
- Session lifecycle: single-use enforced (second POST 410), TTL expiry, cross-session
  name/user binding.
- Route surface: only the two intake routes respond; everything else 404 empty.
- Value hygiene: value never appears in Connect DB, logs, or any response (sentinel fuzz).
- Marker: `[[secret-request: ...]]` stripped from delivered text, button attached,
  malformed marker inert.
